## Smallest coherent design

Keep Flask, manifests, the single worker, existing endpoints, two persistent audio decks and HLS. Consolidate their state before changing the presentation. No second player, queue service, database, websocket layer or acquisition pipeline.

### Small state model

Use `TrackRecord` as the common projection of existing search results and validated manifests, not another persistent catalogue:

- `key`: canonical `youtube:<video_id>`; for imported local items, validated manifest ID. Keep source provider/ID/URL separate from display metadata. Client keys never become filesystem paths.
- Existing title, artist/channel, album and duration; optional `recording_id` plus provenance, genre plus provenance, and matched album/cover reference. Unknown values stay null. Search title/channel similarity is neither recording identity nor genre evidence.
- `saved`: derived from validated original/import records, with original hash/size and paths kept server-side. Existing manifests remain authoritative; optional verified metadata can extend their validated schema compatibly.
- Acquisition: `absent | acquiring | available | failed`; playback readiness: `absent | preparing | playable | failed | expired`, with job ID/media URL and published range where available. Saving/import outcome is separate. `playable` means published decodable media, not “fully downloaded”, “saved” or “beat-analyzed”. Browser buffer readiness is checked separately.

One browser session state owns `currentKey`, ordered upcoming keys, history, skipped/heard keys, autoplay/mode and one monotonic revision. A single map holds TrackRecords/job snapshots. Search results and Library contain references to those records; neither is another queue. Server jobs remain operational work, never an alternative user queue. Keep bounded history and the existing 30-entry user queue cap.

One queue mutation path handles play, add, remove, skip, reorder and refill. Canonicalize and deduplicate current/upcoming identities on every mutation. Repeated add is idempotent. Manual replay remains possible through Play/Previous; automatic repetition waits until eligible unheard tracks are exhausted. Different video IDs remain distinct unless a verified recording identifier or explicit owner-confirmed mapping links them. Even then preserve both source records and bytes; never claim fuzzy audio equivalence or silently replace a selected version.

### Transaction sequence and readiness

1. A row Play action unlocks audio and advances the selection revision. Validate identity/permissions server-side using `video_id`, `body`, `meta`, `guard` and generation checks. Preserve the currently audible deck while a different selection prepares; show the requested title as Preparing. A failed selection leaves explicit retry and the prior track available.
2. Under existing locks, resolve a validated saved original or in-flight same-source job before scheduling acquisition. Promote the existing job instead of creating another. Serialize same-source acquisition across users inside the single worker and recheck saved state after acquiring the slot; retain per-user job/media authorization. Missing/corrupt saved bytes produce a repair error, not silent redownload. A new download needs an explicit repair action and enabled download permission.
3. Reuse `pump_preview`, `publish_assets`, `public` and protected media delivery. Attach as soon as published media and the browser's buffer permit; do not wait for import or analysis. Extend saved-file `cmd_preview` to publish incrementally through the existing notification/cancellation mechanism. Existing HLS is reused while valid; local re-preparation never invokes the provider. Sequential-input early playback and complete-first fallback have distinct status text.
4. Commit current selection only after `safePlay` succeeds and its revision still matches. Discard stale responses; they must not attach media, change the queue, cancel current work or publish stale status. A rejected browser play promise shows Play, not a false Playing label.
5. With autoplay enabled, maintain six upcoming candidates where available, refilling after every consumption/removal. Show all six but prepare only the next two initially; keep one worker. Current then next playback readiness outrank speculative work; optional beat analysis runs after that. Remove search-result audio prefetch. Preserve existing byte/free-space/job limits. Removing candidates, disabling autoplay or changing revision cancels obsolete speculative processes and reaps them; saved bytes and active decks remain protected. Cancelled partial originals are not advertised as resumable: a later restart may repeat prefix bytes.
6. Prepare the next deck from queue head. A normal fade uses `transition({}, {}, duration, fade)` and buffered media, independent of analysis and import completion. Check a finite trustworthy outgoing end and incoming buffer covering the fade before labelling it Ready. Unknown end/buffer means Preparing, followed by ordinary end-to-next playback if necessary. Optional reliable beat data may improve a plan before overlap starts; never revise an active overlap. Preserve gain scheduling, pitch fallback and revision guards; ensure pausing the outgoing deck during commit cannot run the pause-cancellation branch and undo the gain handoff.
7. Atomically consume exactly one queue entry, update current/history, promote saving and refill. A single status poll updates the shared map, readiness and derived views. Save completion triggers `loadLibrary`; entering Library also refreshes it. Polling must never itself attach audio. Save failure keeps playable media distinguishable from a saved recording.

Optional silence support is cue metadata only: validated start/end markers associated with the original hash, disabled by default and reversible. Do not call `cmd_trim`, alter bytes, skip internal gaps or infer silence from quiet music alone. Uncertain boundaries retain the full recording; an automatic cue requires reviewable evidence and user confirmation. Plain fade does not depend on this feature.

### Screens and metadata

- **Now playing:** current title, artist, matched cover, transport and a visible next row with title and Preparing/Ready/error. Queue head and next row must be the same record. “Ready” requires actual buffer readiness. Keep compact transport available across screens; move technical diagnostics into Settings and remove the floating debug/details popup.
- **Library:** downloaded/imported records, one click or keyboard activation to play, secondary Add to queue. Extend existing manifest enumeration to local imported items and resolve those through guarded item lookup plus `cmd_preview`; never send a path from the browser. Refresh after publication without waiting for Navidrome's separate scan. Replace silent 200-item truncation with bounded pagination. Navidrome-only/Managed files have no intake manifest today: their full inclusion requires a bounded adapter using authenticated library IDs and validated local-file mapping. Do not claim all downloaded music is covered until that dependency is implemented and tested; do not create a second catalogue or fetch those files from YouTube.
- **Search:** a result's primary button plays that result directly; retain secondary queue/detail actions. Remove selection radios, the redundant selection bar and all import-file navigation/tab/upload controls from the family UI. Preserve the existing administrator intake API/CLI and safeguards unless separately retired. Remove “Other” and heuristic source badges; exact source attribution belongs in details.
- **Continuation:** same-genre selection uses persisted, sourced metadata. Artist names, Topic status, key and tempo do not establish genre. If genre is unknown, show “Genre unknown” in the relevant selection detail and use honestly labelled queue order/shuffle; if known-genre candidates run out, show that state rather than silently calling unrelated tracks compatible.
- **Artwork:** reuse an exact existing album match where available; store provider album/recording ID and provenance. No title-only automatic match or video thumbnail labelled as album art. Unmatched tracks keep a neutral placeholder. A bounded server-side cover fetch/cache and authorized same-origin image route are necessary additions because none exists today. Validate provider hosts/redirects, size/type and decoded image limits; never accept arbitrary URLs or relax CSP. Matching/provider integration is a dependency, not an accomplished feature; no new service or paid provider is assumed.

Wording cleanup in scope: `templates/index.html` repeats “Saved music” beneath Library and decorates the header with “Private server”; remove these redundant labels. Retain the consequential disclosure that Play saves new recordings to the shared library, plus download/privacy controls and actionable failures.

## Diagnosis and staged acceptance

Before attributing the live failure, capture a selected source ID, saved-manifest validation outcome, job/revision IDs, acquisition start and source-byte count, HLS preparation start, first published segment, first audible playback, import completion and transition readiness. Use sanitized logs; omit credentials, signed provider URLs and private paths. Compare retained original hash/size before and after. A provider media acquisition with received bytes is a download; FFmpeg reading saved bytes is HLS re-preparation. Metadata requests alone prove neither. Invalid manifests, changed source IDs, partial cancellation and expired HLS must be separate outcomes.

Proposed checks, in dependency order; none is claimed passed here:

1. **Identity/storage/backend:** extend `tests/test_music_intake.py`, `test_music_web.py`, `test_music_progressive.py`. Repeated same-ID plays, concurrent users, queue promotion, expired HLS and app-state reconstruction acquire zero new source bytes when a validated original exists. Missing/corrupt originals fail safely. Different IDs remain distinct without explicit identity. Original spool SHA/bytes remain unchanged; imported audio packets remain preserved. Retain auth/CSRF/origin/ownership, path/link/hash, media Range, immutable publishing, collision and cancellation checks.
2. **Queue/readiness:** extend `tests/music_selection.cjs` and backend tests. Repeated adds and bulk Library actions yield zero duplicate current/upcoming keys. With at least six eligible tracks, autoplay shows six and refills after each transition; no more than two speculative preparations are requested. Out-of-order play/queue/poll responses cannot change the latest selection. Removing a candidate or autoplay-off reaps speculative processes and preserves current/saved media. Search causes zero audio acquisitions.
3. **Connected playback:** reuse `tests/music_browser_fixture.py` and `music_browser.cjs`, replacing mocked job/transition success for this journey with the real Flask/intake scheduler. Withhold upstream EOF: require actual browser playback and nonzero decoded signal before release, beyond the existing segment-decode test. For nonsequential input, require truthful complete-first state and exactly one acquisition. With analysis disabled/failed/delayed, a configured four-second fade must produce both deck signals overlapping approximately four seconds (target tolerance 0.5 s in the controlled foreground fixture), no empty gap and exactly one queue consumption. Exercise late next readiness, pause, seek, skip and failed Play during overlap. Observe both channels through commit; a manually injected plan is insufficient.
4. **Owner screenshot complaints:** on phone/tablet/desktop widths verify current and prepared-next visibility, one queue, one-click Library/search playback, automatic multi-track refill, saved tracks avoiding provider downloads, visibly working crossfade, early playback where supported, newly saved tracks appearing within one successful refresh cycle (target five seconds), real matched covers/neutral unknowns, honest genre state, no import UI/Other badges/floating debug popup. Library pagination must expose every validated downloaded record, including local and Managed cases once mapped. Check keyboard activation/focus, accessible names, errors and lack of overlay obstruction; screenshots alone do not pass interaction checks.
5. **Live acceptance:** coordinator/owner repeats the original failing sources and screenshot scenarios on the actual desktop app and physical phone, including background/lock screen, slow network, reconnect and next-track transition. Record source-byte and playback timings alongside audible observations. Physical-device restrictions, unavailable source/provider matching, missing original screenshots or an unreproduced failure stay inconclusive, never synthetic passes.
